# 精算決済 機能追加仕様: L2Transactionチェック

## 1. 概要

### 1.1 目的・背景

精算決済機能に組み合わせて構築することで、L2のログを確認して、精算決済のTransactionのステータスを更新し、精算決済情報を確定する。

### 1.2 適用範囲 / 非対象

* **対象**: チェックL2ログ確認Pod（CronJob）

### 1.3 システム構成概要

- **コンテナ基盤**: Docker / Kubernetes (CronJob)
- **データベース**: PostgreSQL（精算決済情報、送信ログ）

### 1.4 前提・制約

* 精算決済情報は、精算決済側のDBに格納されていることを前提とする
* L2のログは、精算決済側のAWSのS3に格納されていることを前提とする

---

## 2. 機能仕様

### 2.1 基本機能

| 項目 | 内容 |
|------|------|
| 送信トリガー | CronJobによる定期実行 |
| 実行間隔 | CronJob の `schedule` で設定する（日次に限定しない） |
| 多重起動 | 禁止。CronJob の `concurrencyPolicy: Forbid` を設定する。加えて、実行中は PostgreSQL の advisory lock を保持し、ロックを取得できない実行は何もせず終了する |

### 2.2 処理概要

1. Transactionsテーブルから L2 ログ未照合（l2_http_status='pending'）かつ未精算（unsettled）のレコードの tracking_id を抽出
   - 対象はデータ交換完了日時（completed_at、無ければ created_at）が遡及期間（環境変数 `L2_LOG_LOOKBACK_DAYS`、既定 7 日）内のもの
   - 取引可否APIで事前登録しただけ（両当事者とも未報告）のレコードは対象外
2. AWS S3配下のL2のログ(例:20260208-11-0.gz)を、最古の対象取引日の前日〜当日の分だけ取得
3. gzファイルを解凍して、ログから該当のtracking_idのログを抽出
   - レスポンス情報からレスポンスのステータスコードを抽出する
4. Transactionの該当レコードのl2_statusを更新する
5. 遡及期間を超えても未検出のレコードは l2_http_status='timeout' に更新し、後続のキャンセル処理で NP 取引をキャンセルする
6. 確定条件（l2 が 2xx かつ両当事者 completed）を満たすレコードを settled に更新し、NP 請求確定依頼を行う（キャンセル済みのレコードは請求しない）
   - 請求書発行基準日（billIssueBaseDate）はデータ交換完了日（completed_at、無ければ created_at）の JST の日付
   - **NP 側で請求確定に成功したもののみ** request_date を設定する（失敗分は次回実行で再試行）
7. 確定できないレコード（「2.3 確定判定」の表）は NP 取引をキャンセルし、**NP 側でキャンセルに成功したもののみ** settlement_status='cancelled' に更新する（失敗分は次回実行で再試行）
   - 請求確定済み（request_date あり）のレコードはキャンセルしない（下記「請求確定済みの取引」）
8. 請求確定済みだが L2 ログで成功を確認できない（2xx 以外・timeout）レコードは ERROR ログ（`manual recovery required`）で通知する

#### NP API のエラー時の扱い

| NP の応答 | 扱い |
|---|---|
| 成功 | 依頼した全件を成功とする |
| 4xx、または本文に `errors` あり | どの取引が原因か特定できないため、1 件ずつ依頼し直して切り分ける。1 件ずつ依頼しても拒否された取引は ERROR ログを出し、次回実行で再試行する（他の取引の処理は止めない） |
| 5xx・通信エラー | NP 側の障害とみなし、1 件ずつの依頼はせず、全件を次回実行で再試行する |

### 2.3 確定判定

L2 ログ・提供者の報告・利用者の報告の 3 つがすべて成功の場合のみ確定（settled）とする。
L2 ログの成功は statusCode が 2xx（200 に限定しない）であることとする。

| L2 ログ（l2_http_status） | 提供者 / 利用者の報告 | 判定 |
|---|---|---|
| 2xx | 両方 completed | 確定（settled）→ NP 請求確定依頼 |
| 2xx 以外（timeout 含む） | 問わない | キャンセル |
| pending / 2xx | 一方でも failed | キャンセル（failed → completed への変更は API で禁止しているため確定することはない） |
| pending / 2xx | 一方が completed、他方が pending | 遡及期間（`L2_LOG_LOOKBACK_DAYS`）内は保留。超過したらキャンセル |
| pending | 両方 pending（事前登録のみ） | 事前登録から 24 時間経過したらキャンセル |

確定済み（settled）・請求確定済み（request_date あり）・キャンセル済み（cancelled）の取引について、データ交換状態登録・更新 API による状態の変更は 409 で拒否する。キャンセル済みの取引について、取引金額確定 API（利用料モデルなし）による確定も 409 で拒否する。
同じ状態での再送は成功として扱う。

#### 請求確定済みの取引

取引金額確定 API（利用料モデルなし）は L2 ログ突合の前に NP 請求確定を行うため、request_date があり、settlement_status が unsettled の取引が存在する。

| L2 ログ | 判定 |
|---|---|
| 2xx | 確定（settled） |
| pending | 保留 |
| 2xx 以外（timeout 含む） | NP 側で請求済みのため自動ではキャンセルしない。ERROR ログで通知し、手動で確認する |
